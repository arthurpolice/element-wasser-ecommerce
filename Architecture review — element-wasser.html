3 · Wire Stock Reservation expiry to QStash

Strong ports & adapters
src/server/commerce/order-lifecycle.ts — expirePendingPaymentOrders (built, unwired)
src/server/queue/qstash.ts — publish/verify helpers (no production caller)
missing: src/server/jobs/ · src/app/api/qstash/

Problem: payment-pending Stock Reservations only expire when the owner manually triggers a mutation; the QStash seam exists as helpers but has zero adapters in production — a hypothetical seam.

Solution: add the job module and QStash route handler ADR-0004 already prescribes, scheduling expirePendingPaymentOrders; the seam gains its second adapter (schedule + owner mutation) and becomes real.

  • Two adapters justify the seam
  • Stale Stock Reservations stop accumulating
  • Route tests: signature + payload only
  • Job logic already tested via order-lifecycle
Fills the gap ADR-0004 and ADR-0001 explicitly left open — alignment, not conflict.

5 · Make Order Payment Status transitions own their Stock Reservation effects

Worth exploring in-process
src/server/commerce/payment-outcome.ts
src/server/commerce/order-lifecycle.ts
src/server/commerce/order-placement.ts

Problem: understanding "what happens to reserved stock when a Payment fails" requires reading three modules plus ADR-0001's 15-minute rule; payment-outcome flips statuses but never mentions stock, so the coupling is invisible at every seam.

Solution: deepen payment outcome into a transition module where each Order Payment Status change declares its Stock Reservation effect (including "none until expiry") in one place — even if the effect stays expiry-driven.

  • Locality: payment-and-stock rules co-located
  • Tests can assert "session expired → stock unchanged until expiry"
  • Closes the untested webhook → stock integration gap
ADR-0001 caution: eager stock release on Stripe failure would contradict the expiry-based release decision. Deepen the module while keeping expiry-driven release, or reopen the ADR deliberately.

Problem: two routers write Address Book Entries with near-identical Prisma code but different Main Address Book Entry rules — the "exactly one main" invariant has no single owner.

Top recommendation

Candidate 2 — the Order quote module

It is the smallest cut with the widest leverage: one interface replaces four scattered re-implementations of Price, Discount, and Available Stock, it makes preview and placement structurally unable to disagree, and it clears the ground for candidate 1 (Checkout orchestration), which would consume the quote module as its first internal seam.

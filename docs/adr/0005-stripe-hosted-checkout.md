# Stripe hosted checkout

Element Wasser will use Stripe Checkout hosted payment pages for the first card and TWINT payment integration. Checkout places an order, creates a pending Stripe-backed payment, starts a Stripe Checkout Session restricted to the selected payment method, and redirects the customer to Stripe. Stripe's PaymentIntent and Checkout Session state is authoritative. Webhooks are the primary outcome delivery channel; explicit reconciliation reads Stripe as a recovery path after customer return, before Payment Retry, and during operational recovery. Both channels normalize Stripe state and pass it through the same Order-level Payment outcome module. The Stripe Checkout Session and Stock Reservation share a 30-minute payment window. Stock Reservation Expiry must expire the active Stripe Checkout Session before cancelling the Order and releasing stock; if Stripe records success first, the successful Payment wins.

The authoritative Payment Window begins when Stripe creates the Checkout Session, and `paymentExpiresAt` is copied from Stripe's actual Session expiry. Before Session creation completes, the Order uses a 10-minute provisional reservation deadline only so abandoned or failed Session creation can be recovered without holding stock indefinitely. Recovery resumes idempotent Session creation within that period; after it passes, an attempt with no Stripe Session can be cancelled and its Stock Reservation released without contacting Stripe.

Stripe Checkout runs in immediate-capture payment mode, so the commerce model does not represent an authorization-only Payment outcome. Refund Payment records and refunded Order Payment Status remain reserved for the future refund flow.

Checkout Submission is idempotent. The browser creates a random Checkout Submission ID when the Customer confirms placement and reuses it only when retrying that exact submission. The Order stores the ID uniquely plus a fingerprint of the normalized placement input. Repeating the ID with the same fingerprint resolves to the existing Order and Active Payment Attempt; repeating it with different Customer, Cart, address, shipping, or Payment Method data is rejected as a conflict. Stripe Checkout Session creation uses the Payment identity as the provider idempotency key; a pending Payment without recorded Stripe identifiers resumes Session creation rather than being replaced.

Stock Reservation Expiry is a durable two-phase operation. A transaction first claims an expired Order by recording when payment expiry started, while leaving the Order open and its Stock Reservation held. Outside that transaction, the operation asks Stripe to expire the Active Payment Attempt's Checkout Session. After Stripe confirms that the Session is no longer payable, a second transaction verifies that no Payment captured, cancels the Order, and releases stock. Provider failure leaves the expiry marker and Stock Reservation intact for retry. Payment Attempt Replacement and retry are blocked while expiry is in progress; a successful Payment clears the marker and wins.

After Stripe redirects the Customer to the success URL, Order Confirmation hides Payment Retry while the outcome is unresolved. It polls a server reconciliation operation every 30 seconds; that operation reads Stripe and records the outcome through the same Order-level Payment outcome module used by webhooks. Polling continues while Stripe reports a non-terminal outcome and stops when the Payment succeeds, fails, is cancelled, or the Payment Window expires.

## Considered Options

Embedded Stripe Elements was rejected for the first implementation because it would add payment UI and PCI surface area before the product needs that control. Hosted checkout supports both card and TWINT through one Stripe integration path and fits the existing order-first stock reservation model.
